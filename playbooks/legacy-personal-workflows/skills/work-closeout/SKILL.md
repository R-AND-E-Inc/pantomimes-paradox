---
name: work-closeout
description: "Use at a substantive milestone, when preparing a handoff, or when the user asks to capture lessons from repeated rework. Preserve useful project state without creating a new process for every small task."
---

Close the loop on a substantial piece of work with a concise, reliable record.

1. Compare the delivered candidate to the accepted outcome and existing completion rules. State what changed and why, what evidence supports it, and what remains unfinished. Do not infer approval, deployment, merge, or acceptance from implementation alone.
2. If the project already has a state or handoff file, update its appropriate section when task scope authorizes routine documentation. Keep historical decisions intact and link to durable artifacts instead of copying large logs. For projectless work, keep the handoff in the conversation or alongside the deliverable when helpful. Avoid scattering duplicate status files.
3. Record the next action only when real work remains, including any specific blocker or required decision. Preserve enough candidate identity and evidence references for a later task to distinguish this state from newer changes.
4. If the user requests improvement analysis, or repeated rework has a clearly evidenced cause, suggest one narrowly scoped prevention: a missing acceptance criterion, reusable fixture, or clearer project convention. Distinguish user preference from verified technical lessons. Do not automatically rewrite global instructions or promote a one-off workaround into a permanent rule.
5. Give a final answer centered on the outcome, meaningful verification, and material limitations. Avoid restating the entire work log.

Evaluate workflow usefulness by time to an accepted result and repeated corrections, not number of agents, plan length, or test count. For a user-requested pilot, record observed revision cycles and effort when available; never invent speedup percentages or attribute changes to this pack without a reasonable comparison.
