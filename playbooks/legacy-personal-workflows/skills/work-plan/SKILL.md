---
name: work-plan
description: "Use when planning a substantive change, breaking a goal into implementation slices, or preventing ambiguity before a multi-step task. Applies to software and authored artifacts. Skip formal planning for a trivial edit with a clear outcome; do not replace a more specific project planning workflow."
---

Turn the current request into the smallest useful plan tied to observable outcomes.

1. Establish the applicable context. Read the current project's instructions and relevant state, then inspect the actual files or artifacts involved. In a projectless task, use the supplied sources and destination constraints. Separate user instructions from source material. Never import another project's stack, policies, or historical decisions as defaults.
2. Restate the intended outcome and preserve decisions already approved in this conversation or the project's authoritative records. Identify what is excluded only where scope could otherwise expand. Mark assumptions as assumptions. Investigate answerable questions before asking the user; ask only when a missing preference or decision materially affects the result. Continue independent work while awaiting answers.
3. Trace the current behavior or artifact structure. For software, follow the relevant entry point through behavior, data, and visible result. For writing/design/data work, identify inputs, transformation, audience, and final deliverable. Cite inspected locations; do not invent components or assert inspection from filenames alone.
4. Define a few observable acceptance criteria and pair each with a proportionate check. Examples: the saved preference survives reload; a document retains the supplied section order; totals reconcile to the source. For visual work, include inspection of the rendered result. A successful build alone does not establish user-visible behavior.
5. Sequence the smallest coherent changes, their dependencies, and how each will be verified. Surface a migration, compatibility, destructive edit, or unresolved external dependency when it affects sequencing. Use existing project risk rules; do not invent a universal signoff gate, coverage percentage, or agent team.
6. Return a compact plan: outcome, inspected context, acceptance criteria with checks, ordered work, and consequential unknowns. Use the project's plan location/template if one exists; otherwise keep it in the conversation unless persistence helps a long task.

Planning is part of authorized work. If implementation was requested, continue into implementation once material uncertainties are resolved; do not stop for another approval of already authorized work. For a plan-only request, finish with the plan. Do not run all other pack skills automatically.
