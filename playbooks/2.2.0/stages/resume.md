# Resume · current state and the next authorized action

## N01 · Reconcile current truth

Read the resolved project release, applicable instructions, current state/handoff, active contract, and request. Locate the actual current artifact and relevant sources. Verify material claims against files, uncommitted changes, candidate identity, existing results, and authoritative remote state where relevant. Do not run broad suites just to orient yourself. Old pass/done notes do not certify a changed candidate.

Separate completed and evidenced work, in-progress work, available-but-unverified reports, unresolved decisions, and historical rationale. Preserve approved decisions. Fresh observations can correct factual status but cannot authorize changed scope. If state says waiting while a PR/task shows activity, explain the discrepancy and reconcile actual authorization; do not infer either from the other. Read only the task needed for this question and do not interrupt it.

Before inheriting completion, reconcile the unit ID, accepted plan identity and relevant plan changes, current candidate including dirty changes, evidence validity, authorization and next action. A stable path is not a stable plan, and a newer HEAD does not make old results current. Use existing state/register/packet pointers, not another ledger. A short continuation probe is useful after a disrupted handoff: what failed, what changed, what decision still governs, and what action is authorized now? Do not repeat this as ceremony when those facts are already established.

## N02 · Continue without restarting

Identify the smallest next action in the active scope, its real dependency, and consequential uncertainty. Give a short checkpoint then perform the already authorized work. Status-only or handoff-only requests end with that report. Do not replay finished discovery, ask for reapproval merely because the task resumed, or retry a failed approach without changed evidence. Do not automatically switch process versions or rewrite project policy.

Use the existing project-owned state when a durable handoff is needed; for projectless work use the conversation or deliverable companion. Never create a global project-memory store or represent chat recall as verified repository state.
