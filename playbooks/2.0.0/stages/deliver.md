# Deliver · execution, release, and operation

## D01 · Execute the accepted unit

Confirm the authorized outcome, candidate/base, active unit, ownership, and required gates. When the project uses Git, verify the base against the authoritative remote before branching; preserve unrelated changes and other tasks' worktrees. Follow its branch/draft-PR policy; when the project uses pull requests, the pull request body is the completion packet in the shape of `templates/project/.github/pull_request_template.md` unless the project has its own. For nonsoftware work preserve source and deliverable versions without imposing Git. Inspect before editing, implement one coherent outcome, and move behavior checks and documentation deltas with the change where practical. Use synthetic fixtures when the approved data policy requires them.

Maintain one coordinating task under C05. After scope and planning are approved, carry implementation, required review, justified corrections, and verification through their dependencies without returning routine coordination to the user. If the user explicitly requests separate implementation/review tasks, create and manage them with available native tools; otherwise use permitted internal delegation or work locally. Start workers only when their inputs are ready. A fresh reviewer receives the exact candidate and raw requirements/evidence, not the author's reasoning or preferred verdict. Keep resource ownership and task/candidate pointers in the existing handoff; reuse producing contexts for corrections and reassess the integrated candidate.

Use `flow-check` for relevant interactions and `evidence` for adequate checks. Apply C02 before escalating a failure or commissioning another correction: recommend fixing a material defect, diagnosing a consequential unknown, or seeking a narrow scope decision when further work has little practical value. Continue independent authorized work while that decision is pending. Keep optional ideas separate; never corrupt mandated output to pass a faulty check or silently waive an obligation.

## D02 · Review, corrections, and candidate

Apply the project's review tier. Assess and consolidate related findings before assigning corrections; a reviewer suggestion is not automatically required scope. Correct demonstrated material issues and recheck affected behavior. Before another round, explain whether the remaining issue affects actual use and whether the proposed effort is proportionate; recommend a simpler route or an explicit scope decision early. Preserve project-defined attempt/round limits; without one, apply the C06 defaults, stopping an ineffective approach to investigate or seek a fresh bounded review. Substantive correction logic or consequential uncertainty may warrant re-review; wording polish does not. Credible safety/data-loss/migration defects remain unresolved regardless of schedule.

Run targeted checks during work, then the required complete authoritative verification at the project's specified final-candidate point. A new candidate requires the project's invalidation/rerun policy; do not substitute generic evidence reuse for a stricter final-head rule. Present rendered evidence before asking the user for experiential judgment. Human review covers perception, interaction feel, audience fit, tone, and tradeoffs, not manually repeating automated tests. Prepare the final evidence packet and stop at any ungranted merge/publication/release boundary.

At the user's next real decision or approval boundary, apply `steps` in guidance-only mode using the current coordinator/worker state, and close with the C07 handoff. Give the result, your recommendation and tradeoff, the exact decision needed, and only the next copyable prompt(s) the user must supply. Do not hand them implementation/review relay prompts for work you can still coordinate. A pause for one decision does not cancel unrelated authorized work. If delegation is unavailable, state the actual limitation and use a permitted fallback without claiming independent review or background monitoring occurred.

## D03 · Change and hotfix modes

A bounded change uses the existing lightweight contract/delta/evidence surface and no extra phase when project rules allow it. A hotfix repairs an observed released defect with an abbreviated outcome and regression oracle, applicable delta (or restoration of specified behavior), consequence, and evidence. Consequential fixes retain required independent review. Follow the project's emergency authorization and deployment order; verify the released environment when authorized and log the incident/change. Do not create a phase or tag by default.

## D04 · Release readiness

A deployment and a real-user release are distinct. When release is requested, load `library/foundry/references/release-and-operations.md` once and use the project's current release policy and affected consequence. Verify clean reproducibility, realistic input handling, identifiable delivered version, visible errors, recovery/rollback appropriate to the data, credential/data boundaries, and actual delivered experience. Browser emulation does not prove real device audio, orientation, fullscreen, or touch; use the audience/device requirements where relevant.

Public/operated services may additionally need performed restore, rollback, alert and deletion drills, support/response ownership, realistic load evidence, dependency/CI controls, session/recovery checks, and applicable privacy/consent/disclosure obligations. High-consequence delivery needs independent review, authoritative calculation/test oracles, mode isolation, auditability, and a credible recovery path. Select these from actual requirements and mechanisms; do not turn a generic checklist into invented legal/product policy or silently relax an adopted safety gate. A browser-only data limitation is a disclosed retention/recovery risk, not evidence that backup worked.

Record each applicable item as passed, failed, blocked/not run, waived by the proper authority, or not applicable with reason. Honor nonwaivable project controls. Documented drill instructions are not executed drills. Follow project release naming and tagging only when applicable and authorized, then use `closeout`.

## D05 · Operations and sunset

For an incident: establish impact, contain within authorization, repair through the appropriate change/hotfix path, verify, and record cause and prevention only when supported. Route feedback into current corrections, future work, research, or explicit product decisions; do not mutate scope from a support request alone. Reassess consequence when audience, data, autonomy, or irreversible actions change. Review maintenance, dependencies, actionable alerts, stale assumptions, and recovery at the cadence the owner chooses; do not create schedules without a request.

Retirement is deliberate work: handle source/user data under the approved lifecycle, revoke credentials and retire services when authorized, retain required records and a final state, and archive using the project's mechanism. No automatic sunset, publication, or external messages.
