# Start · discovery to the first useful work

## S01 · Enter at the unsatisfied need

For a new or explicitly unadopted project, resolve this stage through explicit `--bootstrap`. This permits preparation under the current user request; it does not install or adopt a profile. An existing project uses its declared release and starts from current evidence, not F0 merely for template conformity. Use `adopt` when the requested outcome is migration of an existing process.

When discovery opens, load `library/foundry/references/discovery-interview.md`; load `classification.md` from the same folder only if the consequence level is unclear. Before any project documents exist, keep discovery in a worksheet made from `library/foundry/templates/foundry-worksheet.md`, or in the conversation for a single-session task.

Read the supplied sources relevant to the request; disclose missing/unreadable material. Separate confirmed facts, working assumptions, decisions, recommendations, and consequential unknowns. Establish the user, problem, primary job, non-goals, real constraints, and success outcome before choosing technology. Do not assume the need for AI, accounts, cloud, native apps, real-time infrastructure, or a database. A fixed technology can be an input when the user actually requires it.

Make useful progress from available evidence. Ask only questions that change a decision, using a recommendation and alternatives where helpful. Never replace a material missing product decision with an assumption just to meet a question limit. Respect delegation and record consequential decisions. Narrate the first-use and returning-user job end to end before declaring discovery sufficient.

## S02 · Product, experience, and architecture

Form a proportionate product contract: audience, jobs, workflows, capabilities, exclusions, observable success, constraints, and labeled assumptions. Classify optional capabilities by current foundation/core need, enhancement, experiment, backlog, or exclusion. Recommendations become scope only through applicable acceptance or delegation. Preserve established IDs and names.

For interactive work, load `library/foundry/references/ux-discovery.md` once, then define device and attention context, navigation by user jobs, first use, routine work, consequential action, and recovery. Specify relevant empty/loading/error/stale/permission states, accessible interactions, and concrete visual references. Unknown/stale values must be distinguishable from zero/healthy. Generated explanations must not masquerade as authoritative data. Use an installed design/browser/artifact skill when it adds the required specialty.

For architecture, load `library/foundry/references/architecture-decisions.md` once and choose the simplest approach supported by the actual requirements. Consider source and lifetime of data, ownership, online/offline behavior, state/concurrency, integrations, reliability, deployment, cost, operator ability, and legacy constraints. Prefer deterministic calculations for deterministic truth. Record consequential choices with credible alternatives, dated external evidence, tradeoffs, and reconsideration triggers. Verify provider capabilities that current foundations depend on. Phase-local mechanical choices can remain open.

Load `library/foundry/references/risk-and-red-team.md` once and assess concrete failure modes of relevant assets: exposure, corruption, deletion, staleness, unavailability, wrong actor, duplicate action, misleading output, or provider loss. For each material risk name a control, detection, accepted residual risk, or a scheduled owner and resolution point. A future research item does not clear a risk that blocks current execution.

## S03 · Program and planning sufficient

Sequence the smallest coherent outcomes with dependencies and evidence, using `plan` for detailed contracts. For software with unproven boundaries, start with a walking skeleton through the actual critical path, including deployment only where applicable, and one meaningful check. If an existing product already proves those boundaries, reuse that evidence. For a document, dataset, or creative project, the equivalent is a small representative deliverable exercising the source-to-output path; do not fabricate a Git/CI phase.

Name the first usable milestone: when the primary job is possible end to end. At that point gather real use evidence and reassess assumptions before committing to the next substantial expansion. Later phases need direction, not premature detailed implementation contracts.

Planning is sufficient when the core workflow is coherent, sources and consequential decisions are resolved, boundaries are credible, acceptance is observable, required risk review is complete, and implementation feedback is more valuable than further ideation. Use `review` for proportionate cross-document consistency and fresh review required by the project or consequential uncertainty. Resolve blockers; retain explicit dispositions for deferred ideas. Do not keep polishing settled wording.

## S04 · Bootstrap only what earns its place

If creating project artifacts is authorized, reuse the project's actual working store or create the requested workspace. Scaffold from the package's `templates/project/` proportionate to consequence: a small single-session utility needs only a README with a five-line contract; a project with persistent data, several modules, or more than one working session gets the document package (root instructions, the operating profile with its adoption block and guidance mode, project state, phase history, and the pull request template when the project uses pull requests). Fill only what applies and delete headings that do not. Maintain one editable source per subject. A small task may need only the conversation and final artifact; a long project may need a brief, current state, active plan, decisions and history. Create risk, runbook, schema, or design documents only when their purpose exists. A chat-only environment can return a portable handoff without pretending it updated a repository. Capability-verified document connectors can be authoritative if the user chooses them; do not inherit a blanket ban on a storage product.

Move discovery content to its continuing owners without losing accepted decisions or pending items; mark archives as historical. Keep stable behavior distinct from progress. Prepare the first coherent prompt and explain the immediate outcome plainly. If the user asked only for planning, stop here. If implementation is authorized and applicable project gates are met, continue through `deliver`. Creating or changing the project's workflow adoption record is a separate explicit action under `adopt`.
